# Serving, optimisation and monitoring: results sheet

## Load test
**Offline stack (fake LLM, 1 worker) — proxy for API overhead only:**
| endpoint | requests | failures | p50 ms | p95 ms | p99 ms |
|---|---|---|---|---|---|
| /ask | 685 | 0 | 570 | 1500 | 3500 |
| /ask/stream | 127 | 0 | 160 | 880 | 2000 |
| /health | 75 | 0 | 130 | 700 | 1800 |

**Real remote stack (bge-m3 + qwen2.5 over the Colab/ngrok tunnel) — `make loadtest USERS=5` (2 min):**
| endpoint | requests | failures | p50 ms | p95 ms | max ms |
|---|---|---|---|---|---|
| /ask | 55 | 0 | 8000 | 15000 | 16000 |
| /ask/stream | 10 | 0 | ~12 (time to headers) | ~56 | 56 |
| /health | 5 | 0 | 4 | 4 | 4 |
`reports/locust_stats.csv` (regenerated by the corrected `run.sh`). `/ask/stream` reports time-to-headers
because locust stops timing once the streamed response opens; the end-to-end `/ask` latency is dominated
by model generation over the free tunnel, **not** the API — `/health` stays ~4 ms under the same load.
The default `run.sh` profile is 50 users, which self-saturates a single free Colab worker (~10 s/answer
serialises 50 concurrent users into timeouts); that profile is meant for a self-hosted/vLLM backend with
real replicas. Run `make loadtest USERS=5` against the tunnel instead. (An earlier `locust_stats.csv`
that showed 3580/3580 failures, `/health` included — captured while the tunnel was down — has now been
**overwritten by this valid 0-failure run**.)
